The full menu of what AgentNexus can do

Every capability is exposed as an API endpoint — a specific URL you hit with a specific action.

POST

/api/v1/auth/token

Mint a JWT token for a tenant. Requires a provisioning secret — so only authorized admins can create tenants.

POST

/api/v1/agents/launch

Start a new agent session with a task plan and context. Returns a session_id — the unique ID you'll use for all future calls on this agent.

GET

/api/v1/agents/{session_id}/state

Inspect what an agent is doing — its current status and the last 5 tool calls it made. Cross-tenant requests return 404, not 403 (see Module 3 for why this matters).

POST

/api/v1/agents/{session_id}/tools/call

Execute a tool within an agent session. The platform records input, output, latency, and status — every action is logged for later analysis.

GET

/api/{tenant_id}/insights

Analytics dashboard: session counts, tool success rates, latency trends — powered by TiDB's columnar engine for fast aggregation without slowing down live traffic.

GET

/api/v1/meta-agent/report

Qwen AI reads the last 24h of agent data and generates optimization recommendations. The AI that watches the AIs.

What "launching an agent" looks like in code

From app/routes/agents.py — the function that runs when you hit POST /api/v1/agents/launch.

CODE 
async def launch_agent(body: LaunchAgentRequest):
    tenant_id  = ctx_tenant.get()
    session_id = str(uuid.uuid4())
    conn = await get_conn(tenant_id)
    async with conn.cursor() as cur:
        await cur.execute(
            "INSERT INTO agent_sessions ...",
            (session_id, tenant_id, body.agent_type, ...)
        )
    return JSONResponse(status_code=201, content={
        "session_id": session_id,
        "status": "planning",
    })
PLAIN ENGLISH

This is the function that runs when you POST to /agents/launch.

Read the tenant ID from the request context — never trust user input for this.

Generate a random unique ID for this new agent session.

Get a database connection belonging to this tenant.

Open a cursor (a pen to write to the database)...

Write a new row to the agent_sessions table...

...inserting the session ID, tenant ID, and agent type.

Send back a "201 Created" response with the new session details.

💡
Aha! The tenant ID never comes from the user's request body. It comes from ctx_tenant.get() — a verified value that was set by the middleware AFTER validating the JWT. This is a key security pattern: never let users claim their own identity in the body of a request.

The components introduce themselves

Imagine the key pieces of AgentNexus in a team standup...

F
FastAPI

Hey team. I'm the web framework. Every HTTP request comes through me. I route it to the right function and send back the response. I also generate the interactive docs at /docs automatically.

M
Middleware

I run before FastAPI even sees the request. I check the JWT token, verify the tenant ID matches, and write the tenant identity to a shared context. If anything's wrong, I return 401 and the request never reaches any route.

F
FastAPI

Wait — so the CORS middleware runs AFTER you?

M
Middleware

Exactly. Middleware layers wrap each other like an onion. CORS is the outermost layer — it runs first on the way IN so even 401 responses get the right CORS headers. I'm the inner layer, running after CORS is satisfied.

T
TiDB Cloud

I'm the database. But I'm not just any database — I'm an HTAP database. I can handle your live agent session writes (OLTP) AND run heavy analytics queries (OLAP) at the same time without one slowing the other. The secret is TiFlash — a columnar copy of the data optimized for aggregation.

P
Connection Pool

And I manage the connection to TiDB so we don't open a new connection on every single request — that would be incredibly slow. I keep 10 connections open per tenant, ready to go. When a request needs the database, it borrows one from me and returns it when done.

Q
Qwen (via DashScope)

I'm the only external AI in the system. I don't run the agents — I watch them. The meta-agent collects 24 hours of execution data and sends it to me. I analyze it and return JSON with failure patterns, optimization suggestions, and an efficiency score.

V
Pydantic (Models)

I'm the bouncer for request data. Before any route function runs, I check that the body has the right shape. If you send agent_type: "hacker", I reject it immediately — only research, codegen, data, and web are allowed. No if-statements needed in the route code.

The clever trick: one database pool per tenant

From app/db.py — a pattern called double-checked locking.

CODE 
async def _get_or_create_pool(tenant_id):
    if tenant_id in pools:
        return pools[tenant_id]
    lock = await _pool_lock(tenant_id)
    async with lock:
        if tenant_id not in pools:
            pool = await aiomysql.create_pool(
                host=TIDB_HOST, maxsize=10, ...)
            pools[tenant_id] = pool
    return pools[tenant_id]
PLAIN ENGLISH

Function: give me a database connection pool for this tenant.

Fast path: if the pool already exists, return it immediately (no locking needed).

We're done — 99% of requests exit here.

Slow path: get a lock that's specific to this tenant (not a global lock!).

Hold the lock while we do the creation...

Check AGAIN — maybe another request created it while we were waiting.

Actually create the connection pool (max 10 connections)...

...and save it so future requests hit the fast path.

Return the pool (whether we just created it or found it already existing).

💡
Why per-tenant pools? If two tenants shared a pool, a heavy request from Company A could starve Company B's requests of database connections. Separate pools give each tenant guaranteed capacity — and make it impossible for one tenant to accidentally affect another's performance.
03

The Security Vault

How AgentNexus makes sure Company A can never see Company B's data — even on shared infrastructure

🔐
Imagine a building with hundreds of safe deposit boxes. The bank employee can access the building, but each box requires the depositor's unique key. Even if you knew the box number, you couldn't open someone else's — and you'd get a polite "not found" rather than a "forbidden" (so you don't even learn which boxes exist).

That's multi-tenant isolation. Let's see how AgentNexus builds it with three interlocking mechanisms.

Layer 1: The wristband — JWT tokens

A JWT is a tamper-proof identity badge. Once issued, it can't be forged or modified.

📋

Header

Says "this is a JWT, signed with HS256 (a type of cryptographic algorithm)."

{"alg": "HS256", "typ": "JWT"}
🏷️

Payload

Contains the actual claims — including tid, the tenant ID that was verified when the token was minted.

{"tid": "enterprise-A", "exp": ...}
✅

Signature

A cryptographic stamp using the server's secret key. If anyone changes the payload (e.g., swaps tenant ID), the signature breaks.

HMACSHA256(header.payload, secret)
💡
Why not just send the tenant ID in the request body? Because anyone could claim to be any tenant. A JWT is signed with a secret only the server knows. If you change "enterprise-A" to "enterprise-B" in the token, the signature fails verification — the tampering is detected.

Layer 2: The checkpoint — tenant middleware

From app/middleware.py — this runs before every protected request.

CODE 
async def tenant_middleware(request, call_next):
    if request.method == "OPTIONS" or \
       request.url.path in _EXEMPT_PATHS:
        return await call_next(request)
    tenant_header = request.headers.get("X-Tenant-ID")
    token = auth_header[len("Bearer "):]
    payload = jwt.decode(token, JWT_SECRET, ...)
    if payload.get("tid") != tenant_header:
        return _mismatch()
    ctx_token = ctx_tenant.set(tenant_header)
    try:
        return await call_next(request)
    finally:
        ctx_tenant.reset(ctx_token)
PLAIN ENGLISH

This security function wraps every request like a locked door.

If it's a browser preflight (OPTIONS) or a public route, skip the check.

(Public routes: /health, /docs, /auth/token.)

Read the X-Tenant-ID header the client sent.

Strip "Bearer " from the Authorization header to get the raw JWT.

Decode and verify the JWT using the server's secret key.

The JWT's "tid" claim MUST match the X-Tenant-ID header exactly.

If they don't match → return 401 and stop. Request dies here.

Write the verified tenant ID to the request-scoped context.

Let the request continue to the actual route handler.

Guaranteed cleanup: clear the context even if something throws an error.

Layer 3: The invisible thread — ContextVar

The secret weapon that makes multi-tenant async safe.

Python's ContextVar is like giving each concurrent request its own sticky note. Even if 100 requests are being handled simultaneously, each one reads its own private copy of ctx_tenant.

❌

The wrong way: a global variable

current_tenant = "enterprise-A"
# Request from B arrives...
current_tenant = "enterprise-B"
# Now request A reads "enterprise-B"!
# 🔥 Data leak
✅

The right way: ContextVar

ctx_tenant = ContextVar("ctx_tenant")
# Request A: ctx_tenant.set("enterprise-A")
# Request B: ctx_tenant.set("enterprise-B")
# A reads its own "enterprise-A" ✓
# B reads its own "enterprise-B" ✓
💡
The finally block in middleware is non-negotiable. ctx_tenant.reset(ctx_token) runs even if the request handler throws an exception. This ensures the context never leaks into the next request that reuses the same async task — a subtle bug that would be nearly impossible to catch in testing.

The 404 trick: hiding what doesn't belong to you

A deliberate security choice that teaches a universal principle.

403

Forbidden (the risky response)

"You exist, I know about you, but you can't access this." This tells an attacker that the session ID they guessed is real — now they know there's something there worth attacking.

404

Not Found (the safe response)

"From your perspective, this doesn't exist." An attacker learns nothing — they can't tell if they guessed the ID correctly. This is called security through obscurity — the session might exist, but you have no evidence either way.

CODE 
await cur.execute(
    """SELECT ... FROM agent_sessions
    WHERE session_id = %s AND tenant_id = %s""",
    (session_id, tenant_id),
)
session_row = await cur.fetchone()
if session_row is None:
    raise HTTPException(status_code=404, ...)
PLAIN ENGLISH

Query the database for a session...

...but ONLY where BOTH the session_id AND tenant_id match.

The tenant ID comes from the verified JWT, not the request.

Get the result (or nothing, if no match).

If nothing was returned — session doesn't exist, OR it belongs to someone else.

Either way, the caller gets "not found" — no information leaked.

The Memory Machine

How AgentNexus stores, queries, and analyzes data across thousands of concurrent agent sessions

🧠
Every agent session, every tool call, every result — it all lives in one place: TiDB. But this isn't just a database. It's a hybrid engine that does both transactions (OLTP) and analytics (OLAP) on the same data, without copying it anywhere.

Let's look at how the schema is built to make multi-tenant isolation natural and fast.

💡
The key insight: tenant_id is the first column in every primary key. This isn't arbitrary — TiDB physically co-locates rows with the same tenant_id together on disk. When you query "give me all sessions for tenant X," the database doesn't scan the whole table. It goes straight to tenant X's region.

Why composite primary keys?

A design decision that makes isolation free, not bolted-on.

⚠️

Simple auto-increment ID

PRIMARY KEY (id)
INDEX (tenant_id)

-- Query needs full index scan:
SELECT * FROM sessions
WHERE tenant_id = 'A'
-- Scans ALL rows, filters by A
-- 🔒 Works, but slow at scale

Every query must filter on tenant_id as a secondary index — extra work.

✅

Composite key (tenant_id, session_id)

PRIMARY KEY (tenant_id, session_id)

-- Query hits the clustered index directly:
SELECT * FROM sessions
WHERE tenant_id = 'A' AND session_id = 'x'
-- Goes straight to tenant A's region
-- ⚡ Fast by construction

tenant_id is baked into the primary key — isolation is physical, not just logical.

Connection pooling — one pool per tenant

From app/db.py — the TiDBPoolManager creates isolated pools.

CODE 
class TiDBPoolManager:
    def __init__(self):
        self._pools: dict[str, Pool] = {}
        self._lock = asyncio.Lock()

    async def get_pool(self, tenant_id):
        if tenant_id in self._pools:
            return self._pools[tenant_id]
        async with self._lock:
            if tenant_id in self._pools:
                return self._pools[tenant_id]
            pool = await aiomysql.create_pool(...)
            self._pools[tenant_id] = pool
            return pool
PLAIN ENGLISH

Each tenant gets their own connection pool (min 1, max 10 connections).

First request from tenant A → create pool A.

Second request from tenant A → reuse pool A (instant).

First request from tenant B → create pool B (separate).

The lock + double-check prevents two coroutines from creating duplicate pools during a race condition.

🔑
Why per-tenant pools? This gives you visibility and control. You can see that tenant A is using 8/10 connections while tenant B is idle. You can rate-limit, quota, or even shut down one tenant's pool without affecting others. It's isolation at every layer.

TiFlash — analytics without slowing down transactions

The same data, two storage engines. Row-based for transactions, column-based for analytics.

📝

TiKV — Row Store (OLTP)

Optimized for single-row operations:

  • INSERT a new session
  • UPDATE tool call status
  • SELECT one session by ID

Fast for point lookups and writes.

📊

TiFlash — Column Store (OLAP)

Optimized for scanning many rows:

  • COUNT failures by agent type
  • AVG latency across 1000 sessions
  • GROUP BY tool_name, status

Fast for analytics — reads only the columns it needs.

CODE 
async def execute_tiflash(tenant_id, sql, args):
    hint = "/*+ READ_FROM_STORAGE(tiflash[agent_sessions, tool_call_history]) */ "
    hint_sql = sql[:offset + 6] + " " + hint + sql[offset + 7:]
    try:
        return await pool_manager.execute(tenant_id, hint_sql, args)
    except Exception as exc:
        # TiFlash unavailable? Fall back to TiKV transparenty.
        return await pool_manager.execute(tenant_id, sql, args)
PLAIN ENGLISH

This helper wraps any SELECT with a TiFlash optimizer hint.

The hint tells TiDB: "use the columnar store for these tables."

The hint is injected into the SQL text after the SELECT keyword.

If TiFlash is ready → columnar speed.

If TiFlash isn't set up yet → transparently falls back to row store.

The caller never needs to handle the fallback — it just works.

The execute pattern — clean, safe, tenant-scoped

Every database call in AgentNexus follows the same pattern.

CODE 
async def launch_agent(body: LaunchAgentRequest):
    tenant_id  = ctx_tenant.get()  # from verified middleware
    session_id = str(uuid.uuid4())
    conn = await get_conn(tenant_id)
    try:
        async with conn.cursor() as cur:
            await cur.execute(
                "INSERT INTO agent_sessions ...",
                (session_id, tenant_id, ...)
            )
    finally:
        await release_conn(tenant_id, conn)
PLAIN ENGLISH

Get the tenant ID from the verified context (set by middleware).

Generate a unique session ID.

Acquire a connection from this tenant's pool.

Execute the query with parameterized SQL (no string interpolation).

The INSERT includes tenant_id — so this row belongs to this tenant only.

Guaranteed cleanup: release the connection back to the pool.

💡
Notice: tenant_id is never taken from the request body. It flows from middleware → ContextVar → get_conn(). The request body can contain any tenant_id it wants — the code ignores it. This is called trusted source, not untrusted input.

Step 1: The analytics query

A single query that joins sessions with tool calls, grouped by agent type, tool name, status, and latency.

CODE 
SELECT
    s.agent_type,
    t.tool_name,
    t.status,
    t.latency_ms,
    COUNT(*) AS cnt
FROM   agent_sessions s
JOIN   tool_call_history t ON s.session_id = t.session_id
WHERE  s.tenant_id  = %s
  AND  s.created_at > NOW() - INTERVAL 24 HOUR
GROUP BY s.agent_type, t.tool_name, t.status, t.latency_ms
PLAIN ENGLISH

For each agent type (research, codegen, data, web)...

...and each tool used (web_search, code_exec, db_query, etc.)...

...count how many calls succeeded, failed, or timed out...

...along with their latency in milliseconds.

Only for this tenant (from the verified JWT context).

Only for sessions created in the last 24 hours.

Grouped so you can spot patterns: "web_search fails 15% of the time after 22:00 UTC."

What the meta-agent returns

The response combines raw data with AI-powered insights.

📊 raw_stats

The raw data from TiFlash — every combination of agent type, tool, status, and latency from the last 24 hours.

🔍 failure_patterns

Natural language descriptions of what's going wrong: "web_search error rate exceeds 15% after 22:00 UTC", "db_query failures correlate with context payloads > 8 KB".

⚡ tool_optimizations

Concrete, actionable fixes per tool: "Add retry with exponential back-off (max 3 attempts, base 500ms); cache identical queries for 5 min".

📈 efficiency_score

A single number (0-100) summarizing how well the agent fleet is performing. Derived from success rate, latency, and resource utilization.

🎯 top_3_recommendations

The three highest-impact changes, ranked by expected improvement: "Parallelise independent tool calls within a session to cut average latency by ~22%".
